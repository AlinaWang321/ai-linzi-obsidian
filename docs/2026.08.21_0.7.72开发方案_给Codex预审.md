## A0. 新发现的 P0 缺陷（Alina 实测，v1 之后）

### A0.1 触发短语解析把说明行当成了短语

Alina 自建的 `jingyancuiqu`（经验萃取）Skill，从「我的 Skills」菜单点击后，输入框被填成 **`AI 霖子自动调用：`** —— 一句废话，当然调不起来。

**复现与定位**（已用脚本逐字复刻解析器逻辑跑通）：

她的 SKILL.md 写法完全正常：

```markdown
## 自动触发

AI 霖子自动调用：          ← 说明句

- 用经验萃取技能            ← 真正的触发短语
```

而 `localSkillAutoTriggersFromMarkdown()`（`local-skill-core.ts`）把该章节内**每一行**都当触发短语（只过滤 4–80 字），解析结果：

```
["AI 霖子自动调用：", "用经验萃取技能"]
                ↑ autoTriggers[0]
```

「我的 Skills」菜单填的正是 `autoTriggers[0]`（`main.ts` 的 `showLocalSkillsMenu`），于是填了说明句。

**修法**：只认 `- ` / `* ` / `+ ` 开头的列表项，普通说明行忽略。

**⚠️ 向后兼容风险（请 Codex 重点看）**：现存 Skill 里可能有人**没用列表**、直接一行行写短语。收紧后这些会变成「零触发短语」。
建议：优先取列表项；**列表项为空时**才退回「取全部非空行」的旧行为。这样既修了 Alina 的问题，又不打断旧 Skill。

### A0.2 Skill Studio 那个字段用户看不懂、也看不见结果

Alina 原话：「这个地方我没有看懂……我不知道这句话到底该怎么设计」。

字段说明写的是「填完整动作句并用逗号分隔」，但用户填完**没有任何反馈**，要等创建完、再去点「我的 Skills」，才发现填进输入框的是什么。

**修法**：字段下方加实时预览——

```
点「我的 Skills」会填入：用经验萃取技能
自动调用命中情况：✅ 自动命中
```

用真正的 `matchLocalSkillInvocation()` 计算（与 §A2 自检同一套逻辑），不另造判断。

## 3. 各步的具体设计

### 步 1 · S8 渲染抽取

`renderCreateLocalSkillOffers`（`main.ts` 5672–5787，116 行）→ `src/create-local-skill-card.ts`。

**纪律**：这一步**只搬不改**。同一提交内不得出现任何行为变更；diff 应当只有「删除 116 行 + 新文件 116 行 + import」。Codex 复审时可用 `git diff -M` 确认是纯移动。

### 步 2 · S1 触发短语解析

```
优先取 /^\s*[-*+]\s+/ 开头的列表项
若列表项为空 → 退回旧行为（取全部 4–80 字非空行），保证旧 Skill 不被打断
```

**S2 官方模板**：`weekly-business-dashboard` 的 `sampleInput` 与 `autoTriggers` 对齐。

Codex 复核结果一并采纳：`consultation-client-workflow` 的 sampleInput 也不逐字匹配（多了「打开的」），但它靠「用 + Skill 名称」走**显式**匹配，当前能正常启动——**因此它不是必须改的缺陷，但自检应当如实显示它是「显式命中、非自动命中」**。

### 步 3 · S3 真实匹配自检

调用真正的 `matchLocalSkillInvocation(sampleInput, [该Skill], { allowAutomatic: true })`，输出三态：

| 结果 | 展示 |
|---|---|
| `matched` 且 `automatic === true` | ✅ 自动命中 |
| `matched` 且 `automatic === false` | ⚠️ 显式命中（靠「用 + 名称」，不会被自然说法自动触发） |
| 其他 | ❌ 完全不命中——点「立即试运行」调不起它自己 |

**不阻断创建**，只在确认卡与 Studio 里如实显示。

**S4** 用同一函数在 Skill Studio 字段下方实时预览。

### 步 4 · S5 不静默失败（按 Codex 收窄）

**只在下列三种情形**判定「用户确实想调 Skill 但没匹配上」，其余一律沿用现有行为：

1. 消息以 `/技能名` 开头（`slash`）
2. 消息明确出现「技能」或「skill」字样（`mentionsSkillWord`）
3. 消息中出现某个已安装 Skill 的可识别名称

**绝不**因为出现裸的「调用」「使用」就判定失败——「调用 API」「使用这个模板」会被误伤（Codex 指出，v1 这条是错的）。

命中上述情形却无匹配时，明确告知并列出可用 Skill，而不是默默按普通对话处理。

### 步 4 · S6 多候选选择卡

按钮 **直接绑定候选的 `localSkillPath`**，点击后按该路径重新 `resolvePath()` 核验唯一性再执行；**不走「把文字填回输入框」那条路**——两个 Skill 显示名相同时，填文字回去仍然 ambiguous（Codex 指出）。

### 步 5 · S7 回归测试

`normalizeText` 的既有能力补测（空格 / 连字符 / 大小写 / 全角半角），**不新增实现**。

## 4. 关于 Alina 提的另外两个问题（本车次不做，先记录）

### 4.1 「只读一份文件」限制

Alina 的 `jingyancuiqu` 在 SKILL.md「输入范围」里自己声明了「每次只处理用户明确指定的一篇文件 / 不自动扫描 `$RAW/`」，插件据此把本轮锁死（`localSkillForbidsVaultExpansion`），所以她说「raw 文件夹的课程逐字稿」时被拒。

**这是按她自己的声明正确执行，不是缺陷。** 但她的真实用法需要「在 `$RAW/` 里检索候选、多份时让我选」。

短期：改她那个 Skill 的声明即可（用户侧，不用改插件）。
长期：是否要在协议里支持「可检索候选 + 命中多份时出选择卡」这一档，建议放到 0.7.73 与删除协议一并设计——**本车次不做**。

### 4.2 「调用 Skill 还要一步步确认吗」

已向 Alina 说明：**确认卡与积分无关，是写入保护**。分界线是「会不会动你的文件」：

- 读取 / 搜索 / 列目录 / 生成内容 → 不确认
- 新建 / 覆盖 / 移动 / 删除文件、上传发布 → 必须确认

她的不满其实指向 §4.1——**在「读」的阶段就被反复卡住**，让人误以为处处要确认。修好 4.1 才是正解，写入确认不动。
