## A. Skill 触发匹配

### A.1 现状与故障复现

Alina 安装官方模板 `weekly-business-dashboard` 后反复调不起来，22 步 127 秒后撞空承诺护栏。

**根因**：该 Skill 的全部特殊运行时能力都挂在 `input.localSkill?.name === WEEKLY_BUSINESS_DASHBOARD_SKILL_NAME` 上——`read_recent_documents` 批量扫描工具、自动追页（最多 24 页）、放大的结果预算（`WEEKLY_BUSINESS_DASHBOARD_MAX_RESULT_CHARS`）。Skill 没挂上，这些能力一个都没有，Luna 只能用通用 search/read 硬啃七天文档，烧完预算后被护栏拦停。护栏行为正确，它只是在为一个不该发生的困境兜底。

**为什么没挂上**（`src/local-skill-core.ts` 的 `matchLocalSkillInvocation`）：

- 自动匹配要求「用户消息**完整包含**某条 `autoTrigger` 作为子串」
- 该模板声明的 trigger：`生成本周经营周报看板`
- 该模板 `sampleInput`（「立即试运行」按钮替用户填的短语）：`生成本周经营周报交互看板`
- **多了「交互」两个字，子串匹配断开** → 点它自带的「立即试运行」都调不起它自己

Alina 说的「继续」「继续给我生成看板」同样不含完整短语；而「继续」走 `recentLocalSkillPath()` 续跑需要之前真跑过一次（消息上有 `localSkillPath`），一次都没跑起来，续跑也接不上。

已用脚本核对，结论确定：

```
「生成本周经营周报交互看板」 包含 「生成本周经营周报看板」 ? → ❌
「继续给我生成看板，为什么没有办法生成呢？」        → ❌ 不命中任何触发短语
「生成本周经营周报看板」                          → ✅ 命中
```

### A.2 Alina 的提议与我的分歧

> Alina：「但凡提到调用和使用、用『技能』跟『skill』，应该都是模糊语言，都要调用这个技能吧？」

**我不建议做成「提到技能就调用」**，理由是会过度触发：

- 「我有哪些**技能**」→ 会去执行某个 Skill 而不是列清单
- 「这个**技能**写得不好，帮我改改」→ 会执行它而不是改它
- 「帮我建个**技能**」→ 与 Skill Creator 抢（代码注释里已记录过这个冲突：`skill-studio-core.ts:45`）
- 装了多个 Skill 时几乎必然 ambiguous

但她指出的痛点是真的：**用户说大白话，现在匹配太死，而且失败是无声的**。所以方向对，做法要换。

### A.3 建议方案：四层放宽，宁可问一句也不静默降级

**A.3.1 自动匹配：整串子串 → 关键词全覆盖**

把 `autoTrigger` 切成关键词，要求用户消息**包含全部关键词**（顺序不限、允许中间插字），而不是包含整串。

```
trigger: 生成本周经营周报看板  →  关键词 [生成, 本周, 经营周报, 看板]

「生成本周经营周报交互看板」      全部命中 → ✅（修好 Alina 的 bug）
「帮我生成一下本周的经营周报看板」 全部命中 → ✅
「继续给我生成看板」             缺 本周/经营周报 → ❌（正确，太泛）
「我有哪些技能」                 无命中 → ❌
```

切词实现：中文按 2–4 字滑窗不可靠，改用**标点与空格切分 + 已声明短语内的自然分段**。具体做法请 Codex 确认取舍：

- 方案 1（推荐）：作者在 SKILL.md 里就用空格分隔关键词，如 `- 生成 本周 经营周报 看板`；未分隔的旧短语退回整串匹配（**向后兼容，旧 Skill 行为不变**）
- 方案 2：插件用词典切分——需引入分词依赖，违反「新增依赖前先扫 dist」的成本，不建议

**A.3.2 显式调用：名字模糊匹配**

`explicit` 分支（用户说了「用/使用/调用/运行/执行」）目前要求消息包含 Skill 的 `name` 或 `triggers` 作为子串。放宽为忽略连字符、空格、大小写后再比对：

```
「用 weekly business dashboard 这个技能」 → 命中 weekly-business-dashboard
「调用经营周报看板技能」                  → 命中（displayName 去标点后匹配）
```

**A.3.3 ⭐ 匹配不到时不许静默降级（本节最重要）**

这是 Alina 真正的痛点——她以为在用 Skill，实际在跟普通对话说话，**而且没有任何提示**。

现行逻辑：`candidates.length === 0` 时，只有 `slash || mentionsSkillWord` 才返回 `missing`（会报错），否则返回 `none`（**静默按普通对话处理**）。

改为：**只要用户消息里出现「技能 / skill / 调用 / 使用」等调用意图词，却没匹配到任何 Skill，就必须显式告知**，并列出可用 Skill 供选择，而不是默默降级。

**A.3.4 多个候选时问一句，不猜**

现行 `ambiguous` 会抛错要求「说出完整技能名」。改为在对话内出一张轻量选择卡（复用 `renderVaultQuestionOffer` 的形态），点一下即选中，不必重新打字。

### A.4 创建时自检（防止再出现「自己调不起自己」）

Skill 创建/更新的确认卡增加一条校验：

- `sampleInput` 必须能命中至少一条 `autoTriggers`
- 命中不了 → 确认卡上**黄色警告**（不阻断创建，Alina 可以坚持）：
  「⚠️ 试运行短语『生成本周经营周报交互看板』匹配不到本 Skill 声明的自动调用短语，点『立即试运行』可能调不起它。建议把 sampleInput 改成『生成本周经营周报看板』。」

**同时修官方模板**：`OFFICIAL_SKILL_TEMPLATES` 里 `weekly-business-dashboard` 的 `sampleInput` 与 `autoTriggers` 对齐。**请 Codex 一并复核其余官方模板有没有同类问题**（我只逐字核过这一个）。

### A.5 明确不改

- 不动 `WEEKLY_BUSINESS_DASHBOARD_SKILL_NAME` 那套专用运行时（追页、结果预算），只修「怎么挂上」
- 不动空承诺护栏与轮次预算
- 不新增依赖

## B. Skill 覆盖 + 版本归档 + 回滚（本车次最高风险项）

### B.1 现状

`src/create-local-skill-vault.ts` 在目录或任一文件已存在时**硬拒**：

```ts
if (app.vault.getAbstractFileByPath(root)) throw new Error(`已存在 ${root}/，为避免覆盖请换一个 Skill 名称`)
```

现有撤销机制 `undoCreatedOutputs()` **只能删掉新建的文件，无法还原被覆盖的内容**。所以「能回撤」的前提是：**覆盖前必须先把旧版完整存下来**。

### B.2 ⚠️ 一个需要 Codex 拍板的技术约束

Alina 已同意把旧版存进 `.versions/`（`.` 开头，Obsidian 文件树默认不显示，不污染）。但有个我**没有实测验证**的前提：

> **Obsidian 的 `app.vault` API 不索引 `.` 开头的目录。**

如果这条成立，`vault.create('.../.versions/1.0.0/SKILL.md')` 会失败或写出来读不回。规避办法是走 `app.vault.adapter`（原始文件系统层），本仓库已有两处先例（`local-skill-executor.ts:270`、`main.ts:2814`）。

**两个候选位置，请 Codex 定：**

| | 位置 | 优点 | 缺点 |
|---|---|---|---|
| **B-1（Alina 已同意）** | `<skillsRoot>/<name>/.versions/<版本>/` | 就在 Skill 旁边，用户想手动翻能翻到；天然是「历史记录」 | 需走 adapter；**Obsidian Sync 不同步未索引文件 → 版本历史是本机的**，换设备回滚不到 |
| B-2 | `.obsidian/plugins/ai-linzi/skill-versions/<name>/<版本>/` | 完全不碰用户 Vault | 用户看不见、也翻不到；同样不同步 |

我倾向 **B-1**（贴合 Alina「历史记录里记版本号」的原意），但**「版本历史不跨设备」这一点必须在 UI 上如实说明**，不能让用户以为换台电脑还能回滚。

**顺带确认**：`isLocalSkillPath()` 要求路径深度 ≤2（`<name>/SKILL.md`），而 `.versions/1.0.0/SKILL.md` 深度为 4，**因此归档不会被误当成 Skill 列出来**——这条我已核过源码，无需额外改动。

### B.3 流程设计

**覆盖时：**

1. 读取当前磁盘上的 Skill 全部文件 + 当前 `skillVersion`（来自 `references/ai-linzi-skill-manifest.json`）
2. 计算差异：新增 / 修改 / 删除（按路径与内容比对）
3. 版本号裁定：模型给的版本 **≤** 当前版本 → 自动 `patch + 1`，并在确认卡说明「模型给的是 1.0.0，与现版本相同，已自动升为 1.0.1」
4. 出确认卡（见 B.4）
5. 用户确认后：**先归档旧版全量到 `.versions/<旧版本>/`，归档成功才开始写**
6. 写入过程沿用现有的失败回滚（写坏了把新写的清掉）
7. 归档保留最近 **5** 个版本，超出删最老的

**回滚时：**

- 入口：「技能」菜单 →「我的 Skills」→ 某个 Skill →「版本历史」
- 列出 `.versions/` 下的版本 + 归档时间
- 选中某版 → 确认卡列出「会把哪些文件改回去」→ 二次确认 → **回滚本身也先归档当前版**（这样回滚也能再撤销）

### B.4 确认卡形态

```
🔄 更新 Skill：weekly-business-dashboard
   1.0.0 → 1.1.0

   修改 2 个：SKILL.md、references/weekly-dashboard-spec.md
   新增 1 个：references/card-spec.md
   删除 0 个

   旧版 1.0.0 会存进 .versions/（本机保留最近 5 版，不跨设备同步）

   ▶ 逐个文件查看差异
   [ 确认更新 ]  [ 取消 ]
```

**红线（请 Codex 重点审）：**

- 归档失败 → **整个更新中止**，不允许「归档不了但照样覆盖」
- 只覆盖本次方案里出现的文件；磁盘上有、方案里没有的文件**默认保留不删**，若模型显式声明删除则在确认卡单列「删除 N 个」
- 不触碰 `.versions/` 自身（写入与差异计算都要排除）
- 二次确认沿用现有 `confirmAction`，与文件写入同一套确认语义

### B.5 需要新增的持久化

**不新增插件设置字段。** 版本信息来源：

- 当前版本 → 读 Skill 自己的 `manifest.json`（已有）
- 历史版本 → 读 `.versions/` 目录名（文件系统即真相源）

这样避免了「设置里记一份、磁盘上一份，两边漂」的老问题。

**边界**：只搬这一个方法及其私有辅助函数，**不动 `main.ts` 其余部分**。这是「有正当理由的第一刀」，不是顺手重构。

## D. 可编辑对话标题

**现状**：0.7.71 已统一 `deriveConversationTitle()`，历史展示**优先用本机正文重新推导**。若用户手工改名，下次打开历史会被重新推导覆盖。

**做法**：`SavedConvo` 新增 `titleEditedAt?: number`（可选，旧记录天然缺省）。

- 有值 → 展示用存储的 `title`，**不再重新推导**
- 无值 → 沿用 0.7.71 的重新推导

**入口**：历史弹窗每行加「重命名」，行内改名，Enter 保存 / Esc 取消。

**边界**：

- **只允许重命名有本机副本的对话**。纯云端对话（来自另一台设备）没有本机 `SavedConvo`，重命名入口置灰并说明原因——**不为此发明新的存储**
- 这是本车次**唯一一个新增持久化字段**，是 `SavedConvo` 上的可选字段，向后兼容
