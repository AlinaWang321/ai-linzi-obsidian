## 一、根因（按影响排序）

### R1 【最高】第 0 轮把 Luna 的推理强度强制关成 none

`webapp/lib/models.ts:91-93`：

```ts
if (Array.isArray(body.tools) && body.tools.length > 0) {
  body.reasoning_effort = 'none'
}
```

`webapp/lib/plugin-vault-agent.ts:157`：

```ts
export function pluginVaultAgentAllowsServerTools(agent) {
  return agent.intent === 'auto' && agent.round === 0 &&
         agent.toolResults.length === 0 && !agent.retryReason
}
```

推导链：intent 恒为 `auto`（见 R2）→ 第 0 轮 `disableServerTools = false` → `chat-core.ts:634` 挂上任务/CRM 原生工具 → Luna 被强制 `reasoning_effort: 'none'` → **第 0 轮零推理**。第 1 轮起 `disableServerTools = true`，不挂工具，推理才恢复。

第 0 轮恰恰是唯一需要做「这句话要不要翻本地文件」这个判断的一轮。我们在它需要动脑的那一秒把脑子关了。这解释了为什么每次新发言（包括「对」「继续」）第一轮总是空口白话，而被逼到后面轮次反而会真去搜。

该行来自 `1f60fd4 fix: 兼容 Luna 插件主对话参数`（2026-07-31）。同批的 `scripts/test-openai-text-provider.mts` 只断言了归一化行为本身，**没有证据表明 OpenAI 真的要求挂 tools 时必须 `reasoning_effort: none`**。这一条必须先复核。

### R2 【高】intent 恒为 auto，最硬的护栏是死代码

- `插件 src/main.ts:2351` 写死 `intent: 'auto'`。
- `插件 src/vault-agent-core.ts:427 detectVaultAgentIntent` 全仓库只被 `isExplicitCurrentNoteTrashRequest` 内部调用过一次，主对话路径永不使用。
- 后端 `buildPluginVaultAgentInstruction` 中 `organize` 分支的强制措辞（「现在禁止输出普通答复、建议或"接下来会检查"等口头承诺；必须立即请求工具」）在主对话中**永远不可达**；`auto` 分支是全部分支里最软的一条。

回归引入点：插件 `a6f2442 feat: let Luna choose Vault tools`（v0.7.30）。那次把路由权交给模型时，把强制条款一起关掉了。

### R3 【高】跨轮状态全丢，且模型自己的记录被清空

- `插件 src/main.ts:2872-2877`：`toolResults` / `pendingRetryReason` / `verifiedWritePaths` 全是 `runVaultAgentLoop` 的局部变量，一次用户发言结束即销毁。用户说「对」时 round 归零、工具结果清空、待办任务不存在。
- `webapp/lib/plugin-vault-agent.ts:372 vaultAgentAssistantTextForHistory`：回复含协议块时**直接返回空字符串**，模型自己也不记得上一轮承诺过什么。

即客户端和模型双向失忆。

### R4 【中】完成判定靠正则，且有一次工具结果就整轮豁免

- `插件 src/vault-agent-core.ts:528`：`vaultAutoAnswerRetryReason` 第一行 `if (hasVaultToolResults) return undefined` —— 一次 `vault_search` 买断整轮豁免权。这是本次「搜到了小B档案却不读取就收尾」能通过的直接原因。
- 正则漏词已实测：`ungroundedSuccess` 动词白名单不含「查」，所以「我先查到…」不命中；`deferred` 收尾组不含「追加」，所以「我继续读取，核对后只追加…」不命中。

### R5 【背景，非本次必修】Vault 工具是散文协议，不是原生工具

同一个请求里存在两套工具机制：原生 function calling（任务/CRM，`chat-core.ts:634`）与文本标记协议（Vault）。system prompt 还叠着 6+ 套互相竞争的标记协议（新建笔记 / 新建文件夹 / 新建Skill / AI图片 / 整理方案 / create_artifact）。模型掉的永远是散文那套。这是 R4 那堆正则存在的根本原因，但属于架构级改动，本工单只作为方向记录。

### 非根因（不要在这上面花时间）

**6 轮上限不是瓶颈。** `VAULT_AGENT_MAX_ROUNDS = 6`（两侧一致），一次发言内绰绰有余。卡住的是**每次按回车状态清零**，不是轮数。不要提高上限。

## 二、修复任务

### P0-0 · 复核并解除第 0 轮的推理封锁（webapp）

**第一步（必须先做，不要跳过）**：写一个一次性探针脚本，直接打 OpenAI，验证 `gpt-5.6-luna` 在 `tools` 非空时是否真的拒绝 `reasoning_effort: 'low'`。

- 分别发 `reasoning_effort` 为 `none` / `low` / 不带 三种请求，各带一个 function tool，记录 HTTP 状态与错误体。
- 结论写进 `docs/开发上下文.md`，脚本用完删除或放 `scripts/` 下并在提交说明中注明是一次性验证。

**第二步，按结论二选一：**

- **若 `low` 可用** → 改 `webapp/lib/models.ts:91-93`，插件 Vault 场景用 `low`（不要一步跳 `medium`，先看成本与延迟）。同步更新 `scripts/test-openai-text-provider.mts` 的断言。
- **若确属硬约束** → 改 `webapp/lib/plugin-vault-agent.ts:157 pluginVaultAgentAllowsServerTools`，让它恒返回 `false`（第 0 轮也不挂云端工具）。代价是任务/CRM 工具晚一轮可用，多一次 API 往返；这个交换划算。同时更新该函数上方的注释，说明为什么第 0 轮不再保留云端工具。

**验收**：第 0 轮请求体中 `reasoning_effort` 不再是 `none`（或 `tools` 为空）。用本工单第四节的回归对话跑一遍，第一句就应发生真实工具调用。

**顺带记录（不必改）**：`normalizeOpenAITextRequestBody` 会删掉 `temperature`（Luna 只接受 1），所以插件里 Luna 实跑 temperature=1，与网页版 0.7 不同。这不是 bug，但请在 `docs/开发上下文.md` 写一句，免得以后当灵异事件查。

### P0-1 · 让 organize 硬护栏重新可达（插件 + webapp）

不要退回 v0.7.29 之前的关键词硬路由（那会牺牲 v0.7.30 的自主判断收益）。改为**升级式路由**：

- 首轮仍走 `auto`，由模型自主判断。
- 一旦满足下列任一条件，**后续轮次**把 `vaultAgent.intent` 升级为 `organize`：
  1. 模型已产出过 `VAULT_ORGANIZE_PLAN`（无论是否被拒）；
  2. 用户本轮句子命中 `isStructuredNoteWriteIntent`；
  3. 存在未结清的 pendingVaultTask（见 P0-2）且其 stage 属于写入流程。
- `intent` 只能单向升级（auto → organize），不允许降级，避免中途反复横跳。

**验收**：写入类任务在第 2 轮起，后端注入的是 organize 的强制措辞，而非 auto 的软措辞。

### P0-2 · 跨轮 pendingVaultTask（插件为主，webapp 配合）

在会话上持久化一个待办任务对象（与现有 `vaultWriteSnapshots` 同级存放，不要进云端历史）：

```ts
interface PendingVaultTask {
  goal: string            // 用户原话摘要
  targetPath?: string     // 已确定的目标文件
  stage: 'searching' | 'searched' | 'read' | 'previewed'
  toolResults: VaultAgentToolResult[]
  createdAt: number
}
```

规则：

- 任务未结清时，**任何**下一轮（不只是「对」「继续」）都把它的 `toolResults` 回灌进 `vaultAgent.toolResults`，并在 instruction 中点名「你上一轮已推进到 X，本轮必须推进到 Y」。不要靠匹配「对/继续/就这样」这类词来触发——那又是一个正则陷阱。
- 结清条件只有三个：出确认卡并被用户确认或取消 / 模型明确声明缺信息并说清缺什么 / 用户显式换了话题（新任务覆盖旧任务）。
- 同步修掉 `webapp/lib/plugin-vault-agent.ts:372`：含协议块时不要返回空字符串，至少留一句结构化摘要（如「已检索 Vault，定位到 X，待读取原文」），让模型自己也有记忆。

**验收**：本工单第四节回归对话中，用户回「对」之后必须直接继续读取 `小B.md`，不得重新开始理解需求。

### P1 · 完成判定从「文本匹配」改为「阶段判定」（插件）

- 删除 `src/vault-agent-core.ts:528` 的 `if (hasVaultToolResults) return undefined` 早退。
- 合法终态只有三种，其余一律 retry：
  1. 本轮输出了真实工具调用；
  2. 明确声明缺信息**并说清缺什么**；
  3. 已产出通过预检的确认卡。
- 新增结构性检查：写入任务中，若 `vault_search` 已命中目标文件但本轮未对该路径 `read_note` 就收尾 → 直接判 retry（`missing_tool_use`）。
- 现有正则**降级为最后一道网**，保留但不作为主判据。

**验收**：「我继续读取，核对后只追加…」这类结尾在写入任务中必被拦截并重试。

### P2 · 用户体验（插件）

- `src/main.ts:2908-2915` 的 Notice 目前只显示「第 N/6 轮」，对用户零信息量。改成实质进度：「已找到 小B.md，正在读取原文…」。
- 硬失败时不要报「请重试」，直接说明卡在哪一步、缺什么。
- 一次任务耗时超过约 30s 时，在对话区（不只是 Notice）给一条可见的进度提示。

### P3 · 方向记录，本次不做

把 Vault 三个只读工具迁到原生 function calling 的 client-side tool 模式（声明工具但不给 `execute`，模型发真 tool call，插件执行后以 tool 消息回填）。这会把「它到底调没调」从模糊文本判断变成 `finishReason === 'tool-calls'`，P1 那整套正则可整体删除。**本次不要动**，先把 P0 落地观察一周，且需先验证 Luna 多工具并发调用的稳定性。写进 `docs/开发上下文.md` 作为待评估项即可。
